※この回の勉強会では上記資料を使用しました。なお、「はじめに」以降の内容は上記資料をもとに作成したものではなく、管理人の備忘録として記載しています。作成途中の内容を含むため、正確性は保証できません。

1. はじめに

前回はローカル環境でDockerを使って、コンテナイメージを作成し、コンテナを起動する流れを学びました。
今回はそのイメージをAWSへ持っていき、AWS上でコンテナを実行して、ブラウザからアクセスできる状態を作ります。

今回使うサービスは次の2つです。

  • Amazon ECR：コンテナイメージを保存する場所
  • Amazon ECS（Fargate）：そのイメージを使ってコンテナを実行する場所

Fargate は、コンテナを動かすためのEC2を自分で管理しなくてよい実行基盤です。タスク定義でCPUやメモリを指定してコンテナを実行できます。Fargate のタスク定義では、CPU とメモリの指定が必須です。

⚠️ 課金に関する注意

今回は学習のため、パブリックサブネット + パブリックIP で最短確認できる構成にします。
ただし、この方法は本番向けの推奨構成ではありません。また、AWSではパブリックIPv4アドレスに課金があり、2024年2月1日以降は 1 IP あたり 0.005 USD/時間 がかかります。新規AWSアカウント向けには Free Tier credits の案内がありますが、無料と決め打ちせず、使い終わったら必ず削除する前提で進めてください。

2. ゴール

この回のゴールは次の3つです。

  • Dockerイメージを ECR に push できる
  • ECS Fargate で コンテナを起動 できる
  • AWS上で動くコンテナへ ブラウザからアクセス できる

3. 解説

3.1 Amazon ECR とは

Amazon ECR（Elastic Container Registry）は、コンテナイメージを保存・配布するためのレジストリです。
ローカルで作った Docker イメージを ECR に push し、ECS がそこから pull して起動します。

学習用としては、Docker Hub のAWS版 と考えると分かりやすいです。
次回以降も、「ローカルで build したイメージを ECR に置く」という流れが基本になります。

3.2 Amazon ECS とは

Amazon ECS（Elastic Container Service）は、コンテナ化されたアプリケーションをデプロイ・実行・管理するためのフルマネージドなコンテナオーケストレーションサービスです。ローカル環境での docker run は「1台のマシン上でコンテナを起動する」操作でしたが、ECS ではそれをより整理し、どのコンテナを、どの設定で、何個、どのように維持して動かすかを分けて管理します。

ECS を理解するうえで重要なのは、クラスター、タスク定義、タスク、サービス の4つです。ECS は単にコンテナを起動するだけの仕組みではなく、設計図を定義し、その設計図から実体を起動し、それを必要数だけ維持するところまで含めて提供します。

クラスター

クラスターは、ECS におけるコンテナ管理の論理的なまとまりです。タスクやサービスは、必ずどこかのクラスターの中で動作します。クラスターそのものがアプリの設定を書く場所ではなく、どのタスクやサービスをどの単位で管理するかを整理するための入れ物です。

Fargate を使う場合でもクラスターは必要ですが、EC2 起動タイプのように「クラスター用のサーバー群を自分で運用する」という意味合いは薄くなります。Fargate では実行基盤の管理を AWS 側が担うため、クラスターは主に管理上の境界として働きます。

タスク定義

タスク定義は、ECS における設計図です。どのコンテナイメージを使うか、どのポートを使うか、CPU とメモリをいくつ割り当てるか、ログをどこへ出すか、どの IAM ロールを使うか、といった起動時の条件をまとめて定義します。ローカルの docker run ではコマンド引数でその場で指定していた内容を、ECS では再利用可能な形で保存する、と考えると理解しやすいです。

タスク定義には、1つだけでなく複数のコンテナを含めることもできます。たとえば、アプリ本体のコンテナに加えて、補助的な処理を行うコンテナを同じタスク内にまとめることができます。つまり、タスク定義は「1コンテナの設定」ではなく、1つの実行単位全体の定義です。

また、IAM ロールには似た名前で役割の違うものがあります。task execution role は、ECS/Fargate が ECR からイメージを pull したり、CloudWatch Logs にログを書いたりするためのロールです。これに対して task role は、コンテナの中で動くアプリケーション自身が AWS API を呼ぶためのロールです。前者は起動のための権限、後者はアプリのための権限です。

タスク

タスクは、タスク定義をもとに実際に起動された実体です。設計図そのものがタスク定義であり、その設計図から起動された「今動いているもの」がタスクです。同じタスク定義から複数のタスクを起動すれば、同じ設定のコンテナ群を複数動かせます。

タスクは起動時にいきなり稼働完了するわけではなく、いくつかの状態を経て実行状態になります。これは、イメージの取得、ネットワークの準備、コンテナ起動などが内部で順番に行われるためです。ECS コンソールで状態が段階的に変わるのは、この流れがあるからです。

サービス

サービスは、指定した数のタスクを維持し続ける仕組みです。単発で1回だけタスクを起動するのではなく、「常に1個動いていてほしい」「常に3個維持したい」といった状態を ECS に管理させるために使います。

サービスの大きな役割は、継続運用と可用性の維持です。必要数より実行中タスクが減れば、ECS は desired count を満たすように新しいタスクを起動します。また、サービス設定やタスク定義を更新すると、新しい設定でタスクを起動し直すデプロイの土台にもなります。Web アプリや API のように継続公開したいシステムでは、サービスが中心的な役割を持ちます。

4つの要素の関係

4つの要素の関係は、次のように整理できます。

  • クラスター：管理のための箱
  • タスク定義：何をどう動かすかを書く設計図
  • タスク：その設計図から起動された実体
  • サービス：その実体を必要数だけ維持する仕組み

この関係が分かると、ECS は「コンテナを起動するサービス」というより、コンテナの実行を設計・実行・維持に分けて管理するサービスだと理解しやすくなります。

3.3 Fargate とは

Fargate は、ECSでコンテナを動かすためのサーバーレスな実行基盤です。
EC2起動タイプのように、コンテナを載せるEC2インスタンスを自分で管理する必要がありません。
その代わり、CPU とメモリ、ネットワーク、イメージ を指定してタスクを起動します。

なお、Fargate の Linux タスクでは、CPUアーキテクチャとして X86_64 と ARM64 が使えます。Mac（M1/M2/M3）でローカル build したイメージを使う場合、アーキテクチャをそろえないと起動に失敗することがあります。

3.4 今回の構成が「学習用」な理由

本番では、ECS/Fargate はプライベートサブネットで動かし、ALB（Application Load Balancer）経由で公開する構成がよく使われます。AWSのベストプラクティスでも、Fargate サービスは private subnet での利用が推奨されています。

ただし今回は、Docker → ECR → ECS の流れを最短で体験するために、

  • パブリックサブネット
  • パブリックIP有効
  • ブラウザから直接アクセス

という、学習用に簡略化した構成を取ります。

4. ハンズオン

Step 0: 事前準備

この回を進める前提は次のとおりです。

  • AWS にログインできる
  • 第6回の内容をもとに Docker イメージを作れる
  • docker と aws CLI が使える
    （ローカルPCでも CloudShell でも可）

AWS CloudShell では、Docker コンテナをビルドして ECR に push する公式チュートリアルもあります。会社PC制限がある場合は CloudShell を使う選択肢もあります。

⚠️ M1/M2/M3 Mac の人へ

Mac でローカル build したイメージを使う場合、ARM64 のイメージになることがあります。
その場合は、後で作るタスク定義の OS/アーキテクチャを ARM64 に合わせる のが簡単です。
逆に、タスク定義を X86_64 にするなら、ローカル側もその前提でビルドする必要があります。

Step 1: ECR リポジトリを作成する

AWSコンソールで ECR を開き、リポジトリを作成します。

  • 可視性設定：プライベート
  • リポジトリ名：aws-study-app（任意）

作成後、リポジトリURI を控えます。例：

123456789012.dkr.ecr.ap-northeast-1.amazonaws.com/aws-study-app

Step 2: Docker イメージを ECR に push する

ここでは、第6回で作ったイメージ、または同等のイメージを ECR に push します。

💡 ヒント

ECR のコンソールには 「プッシュコマンドの表示」 があり、そのままコピペできるコマンドが表示されます。基本的な流れは次のとおりです。

1. ECR へログイン

aws ecr get-login-password --region ap-northeast-1 \
| docker login --username AWS --password-stdin [アカウントID].dkr.ecr.ap-northeast-1.amazonaws.com

2. イメージをビルド

docker build -t aws-study-app .

3. ECR の URI に合わせてタグ付け

docker tag aws-study-app:latest [リポジトリURI]:latest

4. push

docker push [リポジトリURI]:latest

これで、ローカルの Docker イメージが ECR に保存されます。

Step 3: ECS クラスターを作成する

AWSコンソールで ECS を開き、クラスターを作成します。

  • クラスター名：aws-study-cluster
  • インフラストラクチャ：AWS Fargate

クラスター自体は、コンテナを管理するための論理的なまとまりです。
このあと、タスク定義を使ってタスクを起動します。

Step 4: タスク定義を作成する

タスク定義は、ECS版の実行設定ファイルです。
第6回の docker run に相当する設定を、AWS上でまとめて定義します。

設定例：

  • タスク定義ファミリー：aws-study-task
  • 起動タイプ：AWS Fargate
  • OS/アーキテクチャ：
    • Intel/通常PCなら Linux / X86_64
    • M1/M2/M3 Mac で ARM イメージを使うなら Linux / ARM64
  • タスクサイズ：CPU 0.25 vCPU、メモリ 0.5 GB
    （Fargate で有効な最小の Linux 組み合わせの1つです）
  • コンテナ設定例：
    • 名前：app-container
    • イメージURI：Step 1 で控えた ECR URI + :latest
    • コンテナポート：80
💡 ここで追加した方がよい設定

① task execution role

ECS/Fargate が ECR からイメージを pull したり、CloudWatch Logs にログを送るためには、task execution role が使われます。コンソールで自動作成されることも多いですが、存在しない場合は ecsTaskExecutionRole を使う必要があります。

② CloudWatch Logs

コンテナのログを CloudWatch Logs に送るには、タスク定義で awslogs ログドライバを指定します。
ローカルの docker logs に相当する確認手段なので、教材としては入れておいた方が確実です。

Step 5: タスクを実行する

作成したクラスター aws-study-cluster を開き、新しいタスクの実行 を選びます。

設定例：

  • 起動タイプ：FARGATE
  • タスク定義：aws-study-task
  • リビジョン：最新
  • ネットワーク設定：
    • VPC：デフォルト VPC（または勉強会用VPC）
    • サブネット：パブリックサブネット
    • セキュリティグループ：新規作成
      インバウンド：HTTP / 80 / 0.0.0.0/0
    • パブリックIPの自動割り当て：ENABLED ※重要

Fargate タスクはタスクごとに ENI を持ちます。
また、Fargate タスクがコンテナイメージを pull するにはインターネットへの到達性が必要で、パブリックサブネットを使う場合はパブリック IP を割り当てられます。プライベートサブネットを使う場合は NAT Gateway などが必要です。

Step 6: 動作確認

タスク一覧で、ステータスが

PROVISIONING → PENDING → RUNNING

へ進むのを待ちます。

RUNNING になったらタスク詳細を開き、ネットワーク セクションの Public IP を確認します。
その IP に対して、ブラウザで 

http://[パブリックIP]

へアクセスします。前回作成したHTMLが表示されれば成功です。🎉

🔎 表示できないときの確認ポイント
  • セキュリティグループで 80 番を許可しているか
  • コンテナポートが 80 になっているか
  • パブリック IP が有効か
  • タスクのログにエラーが出ていないか

CloudWatch Logs を設定していれば、ローカルの docker logs と同じ感覚で原因を探しやすくなります。

Step 7: 後片付け

課金を防ぐため、作成したリソースは削除します。おすすめ順序：

  1. 実行中タスクを停止
  2. （作った場合）サービスを削除
  3. ECR リポジトリを削除（中のイメージも削除）
  4. タスク定義を登録解除
  5. クラスターを削除
⚠️ 注意

学習用にパブリック IP を使っているため、放置するとパブリック IPv4 料金も含めて課金対象になり得ます。使い終わったら必ず片付けてください。
