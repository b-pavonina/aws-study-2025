1. はじめに

Webサービスのアクセス数は、SNSキャンペーンによる急増や、夜間の減少など一定ではありません。
EC2が1台だけだと、アクセスが増えたときにその1台に負荷が集中します。その結果、表示が遅くなったり、障害時にサービスが止まる恐れがあります。
逆に、ピークに備え常に複数台使用した場合、平常時にはリソースが余りコスト効率が下がります。

こうした課題は、アクセス状況に応じてEC2の台数を柔軟に増減させることで解決できます。今回は負荷に応じてサーバーを自動増減させるスケーラブルな構成と、その監視について学習します。以下のAWSサービスを使います。

  • ALB(Application Load Balancer)
  • ASG(Auto Scaling Group)
  • CloudWatch
  • Session Manager

2. ゴール

  • Multi-AZで可用性（Availability）を上げる考え方を理解する
  • ALBで「入口（DNS）を固定しつつ分散・ヘルスチェックする」仕組みを理解する
  • ASGで「負荷に応じた増減（スケールアウト/イン）」を体験する
  • CloudWatchの「アラーム」を確認し、スケーリングの判断に使われることを理解する
  • Session Managerで 鍵なし・SSHなし の運用アクセスを体験する

3. 解説

3.1 ALB（Application Load Balancer）とは

ALB は、HTTP/HTTPS のリクエストを受け取り、転送先（ターゲット：EC2、IPアドレス、Lambdaなど）へ振り分けて届ける AWS のロードバランサーです。

WebサイトやAPIなどにアクセスが集中すると、1台のサーバーだけでは処理しきれず遅延や障害が起きやすくなります。そこで ALB が入口（窓口）となり、受け取ったリクエストを複数台のバックエンドサーバーへ分散して転送することで、負荷を分散し、台数を増やしてスケールしやすい構成にできます。
また、ヘルスチェックに失敗した転送先にはリクエストを送らないため、障害時でも影響を広げにくい特徴があります。

ALBとAuto Scalingグループを使用した構成図（公式link）

ELB（Elastic Load Balancing）と、その種類

AWSのロードバランサーは ELB（Elastic Load Balancing）というカテゴリにまとまっており、用途に応じて種類があります。

  • ALB（Application Load Balancer）：レイヤー7（L7）。HTTP/HTTPS向け。URLパスやホスト名など、リクエスト内容を見て振り分けできる
  • NLB（Network Load Balancer）：レイヤー4（L4）。TCP/UDP向け。高スループット・低遅延での転送が得意
  • GWLB（Gateway Load Balancer）：セキュリティ製品（FW/IDS/IPSなど）を挟む用途向け
  • （参考）CLB（Classic Load Balancer）：旧世代。既存システムで見かけることはあるが、新規は基本ALB/NLBが主流

この勉強会では、Webサービスの入口として使いやすい ALB を扱います。

ALBの特徴

ALBは、アプリケーション層（L7）でリクエスト内容を見て振り分けを制御できる点が特徴です。

例：

  • パスベースルーティング：/api はAPI用、/ はWeb用へ
  • ホストベースルーティング：admin.example.com は管理画面用、www.example.com は一般向けへ

また、スケーラブル構成の基盤として重要な機能も持っています。

  • 入口を1つに固定できる：EC2が増減しても、ユーザーは同じ入り口(ALBのDNS名)へアクセスし続けられる
  • 負荷分散できる：複数台へ転送して、1台への集中を避ける
  • ヘルスチェック：不調な宛先には転送しない（復旧すれば戻る）

ハンズオンではHTTPを使用しますが、HTTPSの復号をALBで行うことも可能です。

  • TLS終端（ALBでHTTPSを受けて復号する）：ALB に証明書（ACM）を設定すると、ブラウザ↔ALB 間を HTTPS にできます。これにより、証明書の管理を ALB 側に集約でき、バックエンド（EC2など）へ証明書を配布・更新する手間を減らせます。
    ※ バックエンド（ALB→EC2）は HTTPでも運用されることが多い（要件によりHTTPSも可）。

ALBを構成する重要パーツ

  • リスナー（Listener）：どのプロトコル/ポートで受付するか（例：HTTP 80）
  • ルール（Rules）：どこへ送るかの条件分岐（ホスト名・パスなど）
  • ターゲットグループ（Target Group）：転送先（EC2など）をまとめた宛先リスト
    ※AWSでは、ロードバランサーの転送先を ターゲット（Target） と呼び、転送先のまとまりを ターゲットグループ として管理します。

なぜスケーラブル構成でALBが必要なのか

ASGで台数が増減しても、利用者がアクセスする入口（DNS）を固定したまま、裏側を自動で入れ替えられるのがALBの役割です。

ALBの可用性設計（マルチAZ）

可用性のため、ALBは通常2つ以上のAZにまたがるサブネットを選んで作成します。

3.2 Auto Scaling グループ（ASG）とは

Auto Scaling グループ（ASG）は、EC2 インスタンスの台数と状態を、指定したルールどおりに保つための仕組みです。
ASGがやることは大きく次の2つです。

1) 台数を保つ（キャパシティ管理）

ASGでは、あらかじめ 希望する容量／最小の希望する容量／最大の希望する容量 の台数を決めます。
負荷に応じて EC2 を起動／終了し、最小から最大の容量の範囲で台数を増減させます。

  • 希望する容量：最初の台数
  • 最小/最大の希望する容量：増減の下限／上限

2) 異常なEC2を置き換える（ヘルスチェック連動の自動置換）

ASGは、ヘルスチェックで異常と判断したインスタンスを 終了 → 新規起動 で置き換えます（自動置換）。
このときヘルスチェックは、次の2系統があります。

  • EC2ステータスチェック：OS/ハード障害などの基本的な異常検知
  • ELB（ALB/ターゲットグループ）ヘルスチェック：アプリが応答できているかまで含めた検知

ASGがEC2を作るための「設計図」：起動テンプレート

ASGがEC2を起動するときは、起動テンプレート（Launch Template） を使います。
AMI／インスタンスタイプ／セキュリティグループ／IAMロール／User Data などをまとめて定義でき、スケールアウト時も同じ設定のEC2を自動で増やせます。

※ 台数を増やすことを スケールアウト、減らすことを スケールイン と呼びます。

どの基準で増減するのか（スケーリングポリシー）

スケーリングポリシー（Scaling Policy）は、ASGが「いつ・どれだけ増やす／減らすか」を決めるルールです。
ポリシーは CloudWatch のメトリクスなどを材料にして判断し、条件に合えば 台数を増減させます。

スケーリングの主な方法

主に次のパターンがあります。

A) 動的スケーリング（メトリクス連動）

CloudWatch メトリクスをもとに負荷状況に応じて自動で増減します。代表的なポリシーは次のとおりです。

  • ターゲット追跡（Target Tracking）：メトリクスを「目標値」に近づけるよう自動調整（例：平均CPU 40%を維持）
    ※内部的に CloudWatch の仕組み（必要に応じてアラーム等）を利用して動作します
  • ステップスケーリング（Step Scaling）：しきい値超過の度合いで増減量を段階的に変更（例：CPU 60%で+1、80%で+2）
  • シンプルスケーリング（Simple Scaling）：しきい値を超えたら一定量増減（学習向けだが調整はやや粗め）

よく使う判断材料（メトリクス例）

  • CPU使用率（学習向き）
  • RequestCountPerTarget（1台あたりのリクエスト数）
  • TargetResponseTime（応答時間）
  • カスタムメトリクス（例：SQSのキュー滞留数 など）
B) スケジュールスケーリング（時間で増減）

「平日9時は増やす」「深夜は減らす」など、決まった時刻に Desired 台数を変更します。
アクセスパターンが読みやすい業務システムで有効です。

C) 予測スケーリング

過去の傾向から需要を予測し、増える前にスケールアウトします。
「増えてから増やす」だと間に合わない時間帯ピークに強いです。

3.3 Multi-AZとは（可用性を上げる配置戦略）

ここまでの仕組み（ALB＋ASG）を、障害に強くするのがMulti-AZです。
複数のEC2があったとしても、1つの同じAZだけで構成されていた場合、そのAZで障害が発生するとサービス全体が止まる可能性があります。

複数AZにEC2を分散し、ALBで振り分けることで、いずれかのAZに問題が起きても継続しやすい構成になります。

ポイント

  • Multi-AZは「台数を増やす仕組み」ではなく、サービスを止まりにくくする配置戦略です。

3.4 CloudWatch とは（モニタリングの基本：メトリクス / ログ / アラーム）

CloudWatch は、AWS上のリソースの状態を見える化し、必要に応じて通知や自動対処につなげるためのサービスです。
モニタリングの基本は、次の3つをセットで捉えることです。

  • メトリクス（Metrics）：システムの状態を「数値」で見る（例：CPU、リクエスト数、遅延）
  • ログ（Logs）：何が起きたかを「記録」で追う（例：アクセスログ、エラーログ、アプリログ）
  • アラーム（Alarms）：異常の兆候を検知して「知らせる／動かす」

※実務では、よく見るメトリクスを CloudWatch Dashboard にまとめ、アラーム通知は SNS（メール等） に送る構成が一般的です。

1) メトリクス（Metrics）とは

メトリクスは、CPU使用率やリクエスト数などの時系列の数値データです。
グラフで追えるため、「いま負荷が高いのか」「いつから悪化したのか」を感覚ではなく数値で把握できます。

例（今回関係するもの）

  • EC2：CPU使用率（CPUUtilization）
  • ALB：RequestCountPerTarget（1台あたりのリクエスト数）、TargetResponseTime（応答時間）
  • ASG：Desired / InService（稼働台数。ASG画面やEC2台数で確認）

2) ログ（Logs）とは

ログは「何が起きたか」を後から追える証拠です。
メトリクスで異常を見つけたら、原因はログで掘る、という流れが基本になります。

例（今回の構成で関係するログ）

  • Webサーバー（Apache）：アクセスログ / エラーログ
  • OS：システムログ
  • ALB：アクセスログ（※基本は S3へ出力。CloudWatch Logs ではありません）

3) アラーム（Alarms）とは

アラームは、メトリクスがしきい値を超えた（または下回った）ときに状態を変え、通知やアクションを実行できる仕組みです。
例えば「CPUが40%を超えたらアラーム状態にする」といった設定ができます。

今回の構成で CloudWatch は何をしているのか

今回のスケールアウトは、ASGの 動的スケーリング（ターゲット追跡） により実行されます。
ASGのスケーリングポリシーが CloudWatch のメトリクスを参照し、目標値に近づくように台数を増減させます。

次のような流れになります。

  • メトリクス：CPU使用率が上がる（グラフで確認）
  • アラーム：しきい値に達して状態が変わる（OK → ALARM など）
  • 自動対処：ASGが判断してスケールアウトする

3.5 Session Manager

Session Managerは、AWS Systems Managerの機能の1つで、SSHなしでEC2に接続できます。
ブラウザ（AWSマネジメントコンソール）から接続でき、キーペア管理や22番ポート公開が不要になります。
そのため、ASGで増えたインスタンスにも同じ方法で入れて、運用をシンプルにできます。

4. ハンズオン

実際にALBとAuto Scalingを構築し、CPU負荷をかけて自動的にサーバーが増える様子を観察します。
運用アクセスは Session Manager を使います。

ℹ️ 事前準備

VPC: session2-vpc（第2回で作成したVPC）
サブネット: 以下のパブリックサブネット二つ

  • session4-public-subnet-a（第2回のsession2-subnetが残っている場合は、名前変更し流用可）
    • IPv4 CIDR：10.0.0.0/24
    • AZ：ap-northeast-1a
  • session4-public-subnet-c
    • IPv4 CIDR：10.0.1.0/24
    • AZ：ap-northeast-1c

※ 第2回のサブネット作成を参考に準備してください。パブリックIPv4アドレスの自動割り当てを有効化とルートテーブルのサブネットへの関連付けが必要になります。
※ 学習用にEC2をパブリックサブネットで起動しますが、実務ではプライベートサブネット＋必要に応じてNAT/Endpointが推奨です。

Step 0: IAMロールの作成 (Session Manager用)

EC2インスタンスがSession Managerと通信できるようにするための権限（IAMロール）を作成します。

  1. IAMダッシュボードの左メニュー「ロール」→「ロールを作成」をクリック
  2. 信頼されたエンティティタイプ: AWSのサービス
  3. ユースケース: EC2 を選択して「次へ」
  4. 許可ポリシー: 検索ボックスに SSM と入力し、
    AmazonSSMManagedInstanceCore にチェックを入れて「次へ」
  5. ロール名: session4-ssm-role と入力して「ロールを作成」

Step 1: セキュリティグループの作成

1. ALB用セキュリティグループ

ALBへのアクセスはHTTPによる自宅のグローバルIPからのみ許可します。また、Session Manager を使うため、SSH（22番ポート）の許可は不要です。

  • 名前: session4-alb-sg
  • インバウンドルール:
    • タイプ: HTTP (80) / ソース: マイIP

2. EC2用セキュリティグループ

EC2へのアクセスはALBからのHTTP通信のみ許可します。外部からEC2へ直接アクセスされる経路を遮断します。

  • 名前: session4-ec2-sg
  • インバウンドルール:
    • タイプ: HTTP (80) / ソース: カスタム (セキュリティグループ session4-alb-sgを選択)

Step 2: 起動テンプレートの作成

Auto ScalingがEC2を自動作成する際の「設計図」となる起動テンプレートを作成します。

1. EC2ダッシュボードの左メニュー「起動テンプレート」から作成します。

2. 以下の情報を入力し起動テンプレートを作成します。

  • テンプレート名: session4-template
  • OS (AMI): Amazon Linux 2023
  • インスタンスタイプ: t2.micro (または t3.micro)
  • キーペア: 起動テンプレートの設定に含めない
  • ネットワーク設定:
    • サブネット：起動テンプレートの設定に含めない
    • セキュリティグループ: session4-ec2-sg を選択
    • パブリックIPの自動割り当て: 有効化
  • 高度な詳細:
    • IAMインスタンスプロフィール: session4-ssm-role を選択 (Step 0で作成したロール)
    • ユーザーデータ:
      以下のスクリプトをコピーして貼り付けます。Webサーバーを起動し、どのインスタンスか分かるように画面にIDを表示するスクリプトです。 
#!/bin/bash
dnf update -y
dnf install -y httpd
systemctl enable --now httpd

# IMDSv2を使ってインスタンスIDとAZを取得して表示
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
INSTANCE_ID=$(curl -H "X-aws-ec2-metadata-token: $TOKEN" -s http://169.254.169.254/latest/meta-data/instance-id)
AZ=$(curl -H "X-aws-ec2-metadata-token: $TOKEN" -s http://169.254.169.254/latest/meta-data/placement/availability-zone)

echo "<h1>Hello from $INSTANCE_ID ($AZ)</h1>" > /var/www/html/index.html

Step 3: ALB (ロードバランサー) の作成

EC2ダッシュボードの左メニュー「ロードバランサー」から作成します。

  1. 「Application Load Balancer」の作成を選択
  2. ロードバランサー名: session4-alb
  3. スキーム: インターネット向け (Internet-facing)
  4. ネットワークマッピング:
    • VPC:session2-vpc
    • アベイラビリティーゾーンとサブネット:
      ap-northeast-1a -> session4-public-subnet-a
      ap-northeast-1c -> session4-public-subnet-c
      2つのAZ (1a と 1c) のパブリックサブネットを選択
  5. セキュリティグループ: session4-alb-sg を選択 (defaultは削除)
  6. リスナーとルーティング:
    • プロトコル: HTTP / ポート: 80
    • ターゲットグループの作成リンクをクリック（新しいタブが開きます）
      • ターゲットタイプ: インスタンス
      • ターゲットグループ名: session4-tg
      • 「次へ」を押し、ターゲットの登録は何もせずに「ターゲットグループの作成」完了
    • ALB作成画面に戻り、更新ボタンを押して session4-tg を選択
  7. 「ロードバランサーの作成」をクリック

Step 4: Auto Scaling グループ (ASG) の作成

EC2ダッシュボードの左メニュー「Auto Scaling グループ」から作成します。

  1. 名前: session4-asg
  2. 起動テンプレート: session4-template を選択し、次へをクリック
  3. ネットワーク:
    • VPCを選択
    • アベイラビリティーゾーンとサブネット: ALBで選択したのと同じ2つのパブリックサブネットを選択
  4. ロードバランシング:
    • 「既存のロードバランサーにアタッチ」を選択
    • 「ターゲットグループから選択」→ session4-tg を選択
    • ヘルスチェックのタイプ: 「ELB」にチェックを入れる（推奨）
  5. グループサイズ:
    • 希望するキャパシティ: 2
    • 最小の希望する容量: 2
    • 最大の希望する容量: 3
  6. スケーリングポリシー (重要):
    • 「ターゲット追跡スケーリングポリシー」を選択
    • メトリクスタイプ: 平均 CPU 使用率
    • ターゲット値: 40
      ※学習用に低めに設定します（通常は70–80程度）。※判定は ASG全体の平均CPU なので、1台だけに負荷をかけるとスケールアウトしにくい場合があります。
  7. 残りはデフォルトのまま「Auto Scaling グループの作成」をクリック

Step 5: 動作確認とモニタリング

1. 負荷分散の確認

EC2インスタンス一覧を見ると、自動的に2台のインスタンスが起動しているはずです。
ロードバランサーの画面から「DNS名」をコピーし、ブラウザでアクセスします。
ページを何度かリロードして、表示される Instance ID や AZ が切り替われば、負荷分散が成功しています。
※ http:// でアクセスする必要があります。https:// では表示されません。

2. 負荷テストとスケールアウトの確認

起動しているEC2の1台に、Session Manager で接続して負荷をかけます。

⏳ 接続ボタンが押せない場合

インスタンス起動直後はSSMエージェントの準備に時間がかかります（1〜2分程度）。
「接続」ボタンがグレーアウトしている場合は、少し待ってからブラウザをリロードしてください。

  1. EC2インスタンス一覧で、起動しているインスタンスの1つを選択し、上部の「接続」ボタンをクリックします。
  2. 「セッションマネージャー」タブを選択し、「接続」をクリックします。
    ※黒い画面（ターミナル）がブラウザの別タブで開きます。
  3. 以下のコマンドを実行して、CPU負荷をかけます。
    4. # CPU負荷を100%にするコマンドをバックグラウンドで複数実行
yes > /dev/null &
yes > /dev/null &
yes > /dev/null &

    ※ 負荷テストを止めたいときは、以下のコマンドを実行します。

    # 【重要】負荷テストを止めたいときは以下のコマンドを実行
# pkill yes
  4. CPU使用率を確認します。
    top コマンドを実行し、%CPU の値が上がっていることを確認します。
    ％CPUの値の例: 64.3 us, 35.7 sy(二つの合計値が100%に近いほどCPUがフル稼働している状態)
    # CPU使用率を確認（topコマンドの終了は 'q'キー）
top
  5. 数分待ち、CloudWatchのアラーム状態やASGのアクティビティタブ、新しいEC2インスタンスの起動を確認します。
⚠️ セッションマネージャーに接続できない時のチェック
  • 起動テンプレートで IAMロール (session4-ssm-role) を選び忘れていませんか？
  • EC2にパブリックIPは割り当てられていますか?(起動テンプレートでパブリックIPの自動割り当てを有効にする必要があります)

3. CloudWatchとスケーリングの確認

負荷をかけたら、AWSマネジメントコンソールで状況を見守ります。
※メトリクスの反映と判定には数分のタイムラグがあります。焦らず待ちましょう。

  • CloudWatch: CloudWatch コンソールで「アラーム（すべてのアラーム）」を開き、ターゲット追跡スケーリングにより自動作成された TargetTracking-...-AlarmHigh-... / TargetTracking-...-AlarmLow-... を確認します。 CPU 使用率（ASG 平均）が 目標値 40% を上回る方向に振れると AlarmHigh 側の状態が変化し(アラーム状態に変わる)、必要に応じてスケールアウトが実行されます（逆に下回ると AlarmLow 側でスケールイン側の判断に使われます）。
  • Auto Scaling: 「アクティビティ」タブを確認すると、3つ目の"Launching a new EC2 instance" というログが表示されます。
  • EC2一覧: 新しいインスタンスが自動的に起動し、合計3台になります。
  • ターゲットグループ: 新しいインスタンスが自動的に登録され、ヘルスチェックが「Healthy」になります。
チェックリスト
  • [ ] CloudWatchのアラームの状態が「アラーム状態」に変わったか？
  • [ ] ASGの「アクティビティ」タブに 3つ目の"Launching a new EC2 instance" が表示されたか？
  • [ ] EC2インスタンス一覧で、新しいインスタンスが増えているか？
  • [ ] ターゲットグループの「Healthy」なターゲット数が増えたか？

Step 6: 後片付け

確認が終わったら、リソースを削除します。

  1. セッションマネージャーで接続しているターミナルで負荷プロセスを停止（インスタンスごと終了されるのでそのままでも可ですが、念のため） 
    pkill yes
  2. Auto Scaling グループの削除: これを削除すると、起動していたEC2インスタンスも自動的に終了（削除）されます。
  3. ロードバランサー (ALB) の削除
  4. ターゲットグループの削除
  5. 起動テンプレートの削除
  6. セキュリティグループの削除
  7. IAMロール (session4-ssm-role) の削除

5. まとめ

今回は、ALB（入口固定＋分散＋ヘルスチェック）とASG（増減＋自動交換）、CloudWatch（数値監視＋アラーム）を組み合わせて、負荷に応じてスケーリングする構成を体験しました。
Session Managerを使った運用スタイルも体験できたはずです。
