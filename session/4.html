第4回：スケーラブル構成とモニタリングの基本

Posted at 2025-12-30

1. はじめに

Webサービスのアクセス数は一定ではありません。SNS拡散やキャンペーンで急増することもあれば、夜間は減ることもあります。
EC2が1台だけの構成だと、アクセス急増時に落ちたり、逆にアクセスが少ないときにコストが無駄になります。

今回のテーマは 「負荷に応じて自動で増減するサーバー群と、その監視」です。ゴールは次の2つです。

  • アクセスが増えても 落ちにくい構成にする
  • 落ちそうな兆候を 数値で検知して、自動対処できるようにする
⚠️ 課金注意（重要）

このハンズオンでは ALB (Application Load Balancer) を使用します。ALBは起動している時間に対して課金が発生します（無料利用枠は新規アカウント等の条件があるため、対象外の場合があります）。
また、Auto Scalingにより複数のEC2インスタンスが起動するため、長時間放置するとコストがかさみます。
ハンズオン終了後は必ずリソースを削除してください。

2. ゴール

  • Multi-AZで可用性（Availability）を上げる考え方を理解する
  • ALBで「入口（DNS）を固定しつつ分散・ヘルスチェックする」仕組みを理解する
  • ASGで「増減（スケールアウト/イン）＋自動交換（セルフヒーリング）」を体験する
  • CloudWatchで「メトリクス→アラーム→スケーリング」の流れを体験する
  • SSM（Session Manager）で 鍵なし・SSHなし の運用アクセスを体験する

3. 解説

3.1 可用性（Availability）：Multi-AZが必要な理由

なぜ必要か：サーバーやAZには障害が起きる前提で考えます。1台（または1つのAZ）に依存すると、その一点が壊れた瞬間にサービス全体が止まります。

どう使うか：複数AZにEC2を分散配置し、ALBで生きているインスタンスへ振り分けることで、片方のAZに問題が起きてもサービス継続しやすくします。

3.2 ELB (ALB)：分散とヘルスチェック

なぜ必要か：台数を増やしたとき、ユーザーの入口が毎回変わると運用できません。また、死んだサーバーにリクエストを送ると障害時の影響が広がります。

どう使うか：ALBは固定のDNS名を入口として提供し、ターゲットグループのEC2へ分散します。ヘルスチェックで異常なインスタンスを自動的に外せます。

3.3 Auto Scaling：増減とセルフヒーリング

なぜ必要か：負荷が増えたのに台数固定だと遅延・障害につながります。負荷が低いのに台数が多いとコストが無駄です。

どう使うか：ASGで次を実現します。

  • スケールアウト： 負荷が高い → 台数を増やす
  • スケールイン： 負荷が低い → 台数を減らす
  • セルフヒーリング： 異常インスタンスを検知 → 自動で置き換える

3.4 CloudWatch：メトリクスとアラーム

なぜ必要か：システムは感覚ではなく数値（CPU、リクエスト数、レイテンシ等）で状態を把握します。数値で見えると自動化につなげられます。

どう使うか：今回は CPU使用率 のメトリクスを監視し、しきい値超えで アラーム → ASGスケールアウトを体験します。

3.5 SSM（Session Manager）：SSHなしでサーバーに入る理由

なぜ必要か：SSHは鍵管理や22番ポート公開が必要になり、運用事故や攻撃面が増えます。

どう使うか：SSM Session Managerを使うと、キーペア不要、22番ポート不要でEC2へ接続できます。ASGで増えたインスタンスにも同じやり方で入れるため、運用がシンプルになります。

4. ハンズオン

実際にALBとAuto Scalingを構築し、CPU負荷をかけて自動的にサーバーが増える様子を観察します。
運用アクセスは SSM（Session Manager） を使います。

ℹ️ 今回の前提（簡易化）

学習用に、EC2は パブリックサブネットで起動し パブリックIPを自動割り当てします。
ただし運用アクセスは SSHではなくSSM（Session Manager） を使い、22番ポートを開けない方針で進めます。
実務ではプライベートサブネット＋SSM（＋必要に応じてNAT/Endpoint）が推奨ですが、今回は理解優先でシンプルにします。

ℹ️ 事前に決めておくと迷いません

使うVPC、そして 異なる2つのAZのパブリックサブネット（例：ap-northeast-1a / 1c など）を最初に選んでおくと手戻りが減ります。

Step 0: IAMロールの作成 (SSM用)

EC2インスタンスがSystems Manager (SSM) と通信できるようにするための権限（IAMロール）を作成します。先に作っておくと後の手順がスムーズです。

  1. IAMダッシュボードの左メニュー「ロール」→「ロールを作成」をクリック
  2. 信頼されたエンティティタイプ: AWSのサービス
  3. ユースケース: EC2 を選択して「次へ」
  4. 許可ポリシー: 検索ボックスに SSM と入力し、
    AmazonSSMManagedInstanceCore にチェックを入れて「次へ」
  5. ロール名: handson-ssm-role と入力して「ロールを作成」

Step 1: セキュリティグループの作成

ALBはインターネットからHTTPを受け付けますが、EC2は「ALBからのHTTPだけ」を許可することで安全性が上がります。今回はSSMで入るため、SSH(22)は作りません。

1. ALB用セキュリティグループ (ALB-SG)

  • 名前: ALB-SG
  • インバウンドルール:
    • タイプ: HTTP (80) / ソース: 0.0.0.0/0 (Anywhere)

2. EC2用セキュリティグループ (EC2-SG)

  • 名前: EC2-SG
  • インバウンドルール:
    • タイプ: HTTP (80) / ソース: カスタム (ALB-SGを選択)
      ※ALBからの通信のみ許可します。SSH(22)の許可は不要です。

Step 2: 起動テンプレートの作成

Auto ScalingがEC2を自動作成する際の「設計図」となる起動テンプレートを作成します。
EC2ダッシュボードの左メニュー「起動テンプレート」から作成します。

  • テンプレート名: handson-template
  • OS (AMI): Amazon Linux 2023
  • インスタンスタイプ: t2.micro (または t3.micro)
  • キーペア: キーペアなし (SSMを使うため不要です)
  • ネットワーク設定:
    • セキュリティグループ: EC2-SG を選択
    • パブリックIPの自動割り当て: 有効化
  • 高度な詳細:
    • IAMインスタンスプロフィール: handson-ssm-role を選択 (Step 0で作成したロール)
    • ユーザーデータ:
      以下のスクリプトをコピーして貼り付けます。Webサーバーを起動し、どのインスタンスか分かるように画面にIDを表示するスクリプトです。 
#!/bin/bash
dnf update -y
dnf install -y httpd
systemctl enable --now httpd

# IMDSv2を使ってインスタンスIDとAZを取得して表示
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
INSTANCE_ID=$(curl -H "X-aws-ec2-metadata-token: $TOKEN" -s http://169.254.169.254/latest/meta-data/instance-id)
AZ=$(curl -H "X-aws-ec2-metadata-token: $TOKEN" -s http://169.254.169.254/latest/meta-data/placement/availability-zone)

echo "<h1>Hello from $INSTANCE_ID ($AZ)</h1>" > /var/www/html/index.html

Step 3: ALB (ロードバランサー) の作成

EC2ダッシュボードの左メニュー「ロードバランサー」から作成します。

  1. 「Application Load Balancer」の作成を選択
  2. ロードバランサー名: handson-alb
  3. スキーム: インターネット向け (Internet-facing)
  4. ネットワークマッピング:
    • VPCを選択
    • マッピング: 異なる2つのAZ (例: 1a と 1c) のパブリックサブネットを選択
  5. セキュリティグループ: ALB-SG を選択 (defaultは削除)
  6. リスナーとルーティング:
    • プロトコル: HTTP / ポート: 80
    • ターゲットグループの作成リンクをクリック（新しいタブが開きます）
      • ターゲットタイプ: インスタンス
      • ターゲットグループ名: handson-tg
      • 「次へ」を押し、ターゲットの登録は何もせずに「ターゲットグループの作成」完了
    • ALB作成画面に戻り、更新ボタンを押して handson-tg を選択
  7. 「ロードバランサーの作成」をクリック
ℹ️ ターゲットグループは「ASGで登録される先」

ALBはターゲットグループを通してEC2へルーティングします。あとでASG作成時に「このターゲットグループに登録する」を指定します。

Step 4: Auto Scaling グループ (ASG) の作成

EC2ダッシュボードの左メニュー「Auto Scaling グループ」から作成します。

  1. 名前: handson-asg
  2. 起動テンプレート: handson-template を選択
  3. ネットワーク:
    • VPCを選択
    • アベイラビリティーゾーンとサブネット: ALBで選択したのと同じ2つのパブリックサブネットを選択
  4. ロードバランシング:
    • 「既存のロードバランサーにアタッチ」を選択
    • 「ターゲットグループから選択」→ handson-tg を選択
    • ヘルスチェックのタイプ: 「ELB」にチェックを入れる（推奨）
  5. グループサイズ:
    • 希望する容量: 2
    • 最小希望容量: 2
    • 最大希望容量: 4
  6. スケーリングポリシー (重要):
    • 「ターゲット追跡スケーリングポリシー」を選択
    • メトリクスタイプ: 平均 CPU 使用率
    • ターゲット値: 40
      ※学習用に低めに設定します（通常は70–80程度）。※判定は ASG全体の平均CPU なので、1台だけに負荷をかけるとスケールアウトしにくい場合があります。
  7. 残りはデフォルトのまま「Auto Scaling グループの作成」をクリック

Step 5: 動作確認とモニタリング

1. 負荷分散の確認

EC2インスタンス一覧を見ると、自動的に2台のインスタンスが起動しているはずです。
ロードバランサーの画面から「DNS名」をコピーし、ブラウザでアクセスします。
ページを何度かリロード（更新）して、表示される Instance ID や AZ が切り替われば、負荷分散が成功しています。

2. 負荷テストとスケールアウトの確認 (SSM接続)

起動しているEC2の1台に、ブラウザから直接接続して負荷をかけます。

⏳ 接続ボタンが押せない場合

インスタンス起動直後はSSMエージェントの準備に時間がかかります（1〜2分程度）。
「接続」ボタンがグレーアウトしている場合は、少し待ってからブラウザをリロードしてください。

  1. EC2インスタンス一覧で、起動しているインスタンスの1つを選択し、上部の「接続」ボタンをクリックします。
  2. 「セッションマネージャー」タブを選択し、「接続」をクリックします。
    ※黒い画面（ターミナル）がブラウザの別タブで開きます。
  3. 以下のコマンドを実行して、CPU負荷をかけます。
# CPU負荷を100%にするコマンドをバックグラウンドで複数実行
yes > /dev/null &
yes > /dev/null &
yes > /dev/null &

# CPU使用率を確認（topコマンドなど。終了は 'q'）
top

# 【重要】負荷テストを止めたいときは以下のコマンドを実行
# pkill yes
⚠️ 接続できない時のチェック
  • 起動テンプレートで IAMロール (handson-ssm-role) を選び忘れていませんか？
  • パブリックIPは割り当てられていますか？（今回は「SSMがAWSのSystems ManagerエンドポイントへHTTPS(443)で到達できる状態」を手早く確保するため、パブリックIP＋IGW経由で外向き通信できる構成にしています。パブリックIP自体が必須という意味ではありません。実務ではプライベートサブネットでもNAT GatewayやVPCエンドポイントで到達性を確保できます）

3. CloudWatchとスケーリングの確認

負荷をかけたら、AWSマネジメントコンソールで状況を見守ります。
※メトリクスの反映と判定には数分のタイムラグがあります。焦らず待ちましょう。

  • CloudWatch: アラーム一覧に TargetTracking-... という名前のアラームが自動作成されます。状態が「OK」から「アラーム」に変わるのを確認します。
  • Auto Scaling: 「アクティビティ」タブを確認すると、"Launching a new EC2 instance" というログが表示されます。
  • EC2一覧: 新しいインスタンスが自動的に起動し、合計3台（または4台）になります。
  • ターゲットグループ: 新しいインスタンスが自動的に登録され、ヘルスチェックが「Healthy」になります。
チェックリスト
  • [ ] CloudWatchのアラーム状態が「アラーム」に変わったか？
  • [ ] ASGの「アクティビティ」タブに "Launching a new EC2 instance" が表示されたか？
  • [ ] EC2インスタンス一覧で、新しいインスタンスが増えているか？
  • [ ] ターゲットグループの「Healthy」なターゲット数が増えたか？

Step 6: 後片付け

確認が終わったら、課金を防ぐためにリソースを削除します。

  1. SSM接続しているターミナルで負荷プロセスを停止（またはインスタンスごと終了されるのでそのままでも可ですが、念のため） 
    pkill yes
  2. Auto Scaling グループの削除: これを削除すると、起動していたEC2インスタンスも自動的に終了（削除）されます。
  3. ロードバランサー (ALB) の削除
  4. ターゲットグループの削除
  5. 起動テンプレートの削除
  6. セキュリティグループの削除
  7. IAMロール (handson-ssm-role) の削除

5. まとめ

今回は、ALB（入口固定＋分散＋ヘルスチェック）とASG（増減＋自動交換）、CloudWatch（数値監視＋アラーム）を組み合わせて、負荷に応じて勝手に強くなる構成を体験しました。
さらに運用アクセスをSSM（Session Manager）に寄せることで、SSH(22)を開けずに管理できる、実務寄りの運用スタイルも体験できたはずです。

次のステップとしては、CPUだけでなく RequestCountPerTarget やレイテンシを使ったスケーリング、さらに実務寄りにプライベートサブネット構成へ寄せる（NAT/Endpoint/SSMの到達性設計）と理解が深まります。
