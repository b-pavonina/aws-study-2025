IAM（Identity and Access Management）の基礎

IAMとは？

IAM（Identity and Access Management） は、AWSにおけるアクセス管理の中核を担うサービスです。
「誰が（アイデンティティ）」「どのリソースに」「どんな操作をできるか（アクセス許可）」を、きめ細かくコントロールできます。

たとえば、開発チームのメンバーごとに操作権限を分けて、誤って本番環境を削除したり、機密情報にアクセスしたりするのを防ぐことができます。
また、IAMを正しく設計しておくことで、万が一不正アクセスが起きた場合にも、影響範囲を最小限に抑えることができます。

つまりIAMは、AWSアカウント全体の「安全の土台」となる存在です。
セキュリティを確保しつつ、チーム全員が安心してクラウドを使えるようにするためにも、IAMの理解と設計は欠かせません。

学習用の個人利用時の位置づけ

学習では次のような使い方をしていればOKです。

  • ルートユーザー … AWSを最初に作るために使う（課金設定など）
  • IAMユーザー（管理者権限） … 実際の操作に使うアカウント

実務にも通じる基本構成です。

実際のプロジェクトでのイメージ

たとえば、会社やチームで1つのAWSアカウントを使って開発する場合、次のような構成になります。

役割 アカウントの種類 権限参考例 説明
代表者 / 管理者 ルートユーザー 全権限（緊急時のみ使用） AWSを最初に作成した人。普段は使用せず、請求やMFA設定など限定用途でのみ使う。
インフラ担当エンジニア IAMユーザー AdministratorAccess（構築期のみ）→運用期は権限分割(最小権限化) VPC、EC2、RDSなどの環境構築を担当。
開発メンバー IAMユーザー AmazonEC2FullAccess(EC2の権限)、AmazonS3ReadOnlyAccess(S3の権限) など 開発・検証環境の利用者。必要なサービスのみにアクセスできる。
監査・セキュリティ担当 IAMユーザー SecurityAudit＋AWSCloudTrailReadOnlyAccess ログや権限設定の確認専用。

💡 なぜこのように分けるのか

  • ルートユーザーは強力すぎるため、誤操作・漏えいのリスクが高い
  • IAMユーザーを分けることで、「誰が・何を・どこまで」できるかを管理できる
  • CloudTrailと組み合わせることで、「誰がいつ何をしたか」を追跡できる
    ※ CloudTrail : AWSの監査ログサービス。AWSアカウント内で「誰が」「いつ」「どんな操作をしたか」を自動的に記録する。
    たとえば、EC2を削除した人やRDSを変更した人を後から確認できます。
  • MFA（二段階認証）を個別に設定でき、セキュリティが向上する

IAMの主な構成要素と役割

IAMは単に「ユーザーを作る」だけの仕組みではなく、 人間・システム・ポリシーを組み合わせてアクセスを制御する総合的な仕組みです。 ここでは、IAMを構成する主な要素を整理します。

構成要素 説明
IAMユーザー 実際の人が使うAWSアカウント。アクセスキーやログインパスワードを持ち、どのAWSリソースを操作できるか個別の権限を設定可能。開発者や運用者に割り当てる。
IAMロール AWSサービスや他アカウントのユーザーに「一時的な権限」を渡す仕組み。EC2やユーザーがロールを引き受け（AssumeRole）、定義された範囲の操作を行う。アクセスキーを持たず、STSによる一時的な認証情報で安全に利用できる。
IAMポリシー 「誰に」「どんな操作を」「どのリソースで」許可または拒否するかを定義するJSON形式のルール。IAMユーザー・ロール・グループにアタッチして適用する。
IAMグループ 複数のIAMユーザーをまとめる単位。グループにポリシーをアタッチすると、所属する全ユーザーにまとめて適用される。権限管理の効率化に有効。

IAMポリシーの書き方

IAMポリシーはJSON形式で記述されます。
以下は一つの例ですが、このポリシーは、「AWS上のすべてのEC2インスタンスに対して、 インスタンスを起動および停止する操作を許可しています。 

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ec2:StartInstances",
        "ec2:StopInstances"
      ],
      "Resource": "*"
    }
  ]
  • Statement： 実際の許可や拒否のルールをまとめたブロックです。
  • Effect 「Allow（許可）」または「Deny（拒否）」を指定します。この例では "Allow" なので、指定された操作を許可します。
  • Action 許可または拒否の対象となる操作を指定します。この例ではEC2の「起動（StartInstances）」と「停止（StopInstances）」が対象です。
  • Resource 操作対象となるAWSリソースを指定します。ここでは "*"（すべてのリソース）となっており、全てのEC2インスタンスが対象になります。

    • 今回のセッションではIAMのハンズオンはしませんが、コンソールからIAMポリシーの確認や作成をすることができます。
    既存ポリシーが用意されており(1407個以上ととても多いですが)、よく使う権限はこれらを利用することが多いです。

    既存ポリシーの一例ですが、中身がJSON形式で書かれているのが確認できます。

IAMとリソースポリシーの違い

IAMでは「ユーザー側の権限設定」だけでなく、 リソース側に直接アクセスルールを設定する方法（リソースポリシー）も存在します。 それぞれの視点を理解しておくと、アクセス制御の仕組みを正しく設計できます。

比較 IAMポリシー リソースポリシー
管理対象 IAMユーザー / ロール / グループ AWSリソース（例：S3, SNS, Lambda）
管理視点 誰に何を許すか 誰をこのリソースに許可するか
主な用途 社内ユーザーやアプリに権限付与 外部アカウントからのアクセス制御など
代表例 AmazonEC2ReadOnlyAccess S3バケットポリシー、Lambdaリソースベースポリシー

➡ IAMポリシーとリソースポリシーは併用可能で、アクセスは「両方で許可」されて初めて成立します。(一部でもDenyだとアクセス不可)。

IAMのベストプラクティス

AWSのIAMは、自由度が高い分、設定を誤ると重大なセキュリティリスクにつながることがあります。 そのため、「便利さ」よりもまず「安全性」を重視した設計と運用ルールが重要です。 以下は、AWSが公式に推奨しているIAM運用の基本原則（ベストプラクティス）です。

原則 解説
最小権限の原則（Least Privilege） 必要最小限のアクセス権だけを与え、誤操作・不正アクセスのリスクを最小化
ルートユーザーは使わない ルートユーザーは緊急時以外使用せず、IAMユーザーで運用する。
MFA（多要素認証）の有効化 すべての管理ユーザーにMFAを適用。盗難・不正アクセス対策として重要
IAMロールの活用 EC2やLambdaなどのAWSサービスには、IAMユーザーではなくロールを付与（アクセスキー不要）
ポリシーの定期見直し 使われていない権限を洗い出し、CloudTrailログを基に最適化を定期的に実施。

🧪 設計パターンの例

シナリオ IAM構成の例
開発者がEC2を操作 IAMユーザー＋AmazonEC2FullAccess ポリシー
EC2からS3にアクセス IAMロール＋AmazonS3ReadOnlyAccess をインスタンスにアタッチ
閲覧だけさせたいユーザーグループ IAMグループ＋ReadOnlyAccess ポリシー
外部アカウントがS3を参照 S3バケットにリソースポリシーを設定（Account ID指定）

(参考) IAM Identity Centerとは？

近年のAWS環境では、IAM Identity Center（旧AWS SSO）を使って チームや組織全体の「ログイン方法」と「アクセス権限」をまとめて管理するケースが増えています。

この仕組みでは、各メンバーが会社のメールアドレスとパスワードで AWSのSSOポータル（Identity Centerポータル）にサインインし、 必要なときだけ IAMロールを一時的に借りて（引き受けて） AWSリソースを操作します。

AWSアカウント内にIAMユーザーを作成する必要がなく、 個別のパスワードやアクセスキーを発行しないため、 セキュリティと運用の両面で管理が非常にシンプルになります。

ただし、AWS Organizationsとの連携が前提となるため、 初期設定にはやや手間がかかります。 そのため、個人学習や小規模チームでは、まずIAMユーザーによる基本的な管理を理解しておけば十分です。

🔚 まとめ

  • IAMはAWSのセキュリティとアクセス制御の核
  • ユーザー・ロール・グループ・ポリシーを適切に使い分ける
  • IAMポリシーとリソースポリシーは別物だが、連携して動く
  • セキュリティ設計の第一歩は、「誰に、どのようなアクセスが必要か」を明確にすること

2. RDS / Auroraの概要

Amazon RDSとは

RDS（Relational Database Service）とは、AWSが提供するマネージド型のリレーショナルデータベースサービスです。

  • 対応エンジン：MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Amazon Aurora(MySQL/PostgreSQL互換)
  • 自動バックアップやスケーリング、パッチ適用などの運用負荷を軽減
    ※ マネージド : ユーザーがインフラ管理を意識せずに利用できるよう、AWSが運用管理を代行するサービス形態。

Amazon Auroraとは

Auroraは、AWSが独自に開発したリレーショナルデータベースエンジンで、MySQLおよびPostgreSQLと互換性があります。
RDSの一種ですが、従来のRDSよりも高性能・高可用性を提供します。

RDSとAuroraの違い

比較項目 RDS（MySQLなど） Aurora
性能（スループット） オープンソースのMySQLをそのまま利用。性能はインスタンスタイプや設定に左右される。 AWS独自のエンジンでクラウド向けに最適化。MySQL比で最大5倍、PostgreSQL比で最大3倍の処理性能。
ストレージ構成 ストレージ容量を手動で指定。拡張するときは再起動やメンテナンスが必要な場合がある。 計算とストレージが分離されており、ストレージは自動で最大128TBまで拡張できる。停止なしでスケール可能。
可用性（高可用構成） Multi-AZ構成を選べる。
① スタンバイ1台（読取不可）
② スタンバイ2台（読取可）のクラスタ構成も選択可能。 		データを3つのAZに6コピーして自動で同期。ストレージ層が冗長化されているため、障害に非常に強い。
冗長化の仕組み プライマリDBとスタンバイDBの間で同期レプリケーション。障害時はスタンバイを自動昇格。 ストレージ層で同期レプリケーションを行うため、計算ノードが落ちてもデータは保持され、すぐ切り替わる。
フェイルオーバー時間 Multi-AZクラスタ構成では、通常35秒以内に自動フェイルオーバー（AWS公称値）。 ストレージを共有しているため、30秒未満でフェイルオーバーが完了することが多い。
読取スケール（読み取り分散） リードレプリカを最大15台まで追加可能。Multi-AZクラスタ構成ではスタンバイ2台も読取可。 最大15台のリーダーインスタンスを追加可能。すべて同じ共有ストレージを使うため、遅延が非常に少ない。
バックアップと復元 1日1回の自動スナップショットとトランザクションログで復元。バックアップ中はI/O性能に軽い影響。 常時自動バックアップ（S3保存＋継続スナップショット）。性能への影響はほとんどなく、いつでもポイント復元可能。
セキュリティ VPC隔離、SSL通信、保存時の暗号化、IAM認証などに対応。 同様に対応。さらにトークンベースのIAMデータベース認証を標準サポート。
コスト 安価でシンプル。開発・検証・小規模本番に向く。 高性能・高可用な分コストは高め。大規模・本番環境に向く。

ハンズオン手順

🔹 1. EC2インスタンス作成

  • 第2回(EC2インスタンス作成)と同じ手順でEC2インスタンスをパブリックサブネットに作成する。

🔹 2. プライベートサブネットの作成

RDS用に、新規でプライベートサブネットを3つ作成する。アベイラビリティーゾーンはそれぞれ異なるものを指定する。

  1. 「VPC」を検索し選択する
  2. 左メニューから「サブネット」を選択し、「サブネットを作成」を押す
  3. 1つ目のプライベートサブネットを以下の内容で設定する
    4. VPC: session2-vpc(第2回で作成したもの)
    サブネット名 : 任意（例 : session3-private-subnet-a)
    アベイラビリティゾーン: ap-northeast-1a
    IPv4 CIDRブロック : 10.0.3.0/24
  4. 左下の「新しいサブネットを追加」を押し、2つ目と3つ目のプライベートサブネットも設定し、作成をする
    5. 【2つ目のプライベートサブネット設定内容】
    VPC: session2-vpc(第2回で作成したもの)
    サブネット名 : 任意（例 : session3-private-subnet-c)
    アベイラビリティゾーン: ap-northeast-1c
    IPv4 CIDRブロック : 10.0.4.0/24

    【3つ目のプライベートサブネット設定内容】
    VPC: session2-vpc(第2回で作成したもの)
    サブネット名 : 任意（例 : session3-private-subnet-d)
    アベイラビリティゾーン: ap-northeast-1d
    IPv4 CIDRブロック : 10.0.5.0/24

  5. 3つのプライベートサブネットが作成されたことを確認する
💡 補足：プライベートサブネットとルートテーブル

Q: プライベートサブネットにルートテーブルは不要なのか？
A: いいえ、プライベートサブネットにもルートテーブルは必要です。

今回のハンズオンでは明示的にルートテーブルを作成していませんが、実はVPCには必ず「メインルートテーブル」が自動で作成されています。
サブネット作成時にルートテーブルを指定しない場合、自動的にこのメインルートテーブルが関連付けられます。

パブリックサブネットとプライベートサブネットの違い：

  • パブリックサブネット：インターネットゲートウェイ（IGW）へのルート（0.0.0.0/0 → IGW）を持つルートテーブルを関連付け
  • プライベートサブネット：IGWへのルートを持たないルートテーブルを関連付け（メインルートテーブルのままでOK）

今回のRDSは、インターネットからの直接アクセスを必要としないため、メインルートテーブル（IGWへのルートなし）が関連付けられたプライベートサブネットに配置しています。
これにより、同じVPC内のEC2からのみアクセス可能な、セキュアなデータベース環境を実現しています。

🔹 3. DBサブネットグループの作成

  1. 検索窓からAurora and RDSを開く
  2. 左メニューから「サブネットグループ」を選択し、「DBサブネットグループを作成」を押す
  3. サブネットグループの詳細を以下の内容で設定し、作成を押す
    DBサブネットグループ名 : 任意（例 : session3-db-subnet-group)
    説明 : 任意（例 : DB subnet group for RDS in session 3)
    VPC : session2-vpc(第2回で作成したもの)
  4. 以下のアベイラビリティーゾーンとサブネットを選択し、作成を押す
    アベイラビリティーゾーン : ap-northeast-1a, ap-northeast-1c, ap-northeast-1d
    サブネット : session3-private-subnet-a, session3-private-subnet-c, session3-private-subnet-d
  5. 作成が完了したことを確認する

🔹 4. RDS用のセキュリティグループ作成

RDS用に新規でセキュリティグループを作成し、EC2からの接続を許可するルールを追加する。

  1. 検索窓からVPCを開く
  2. 左メニューから「セキュリティグループ」を選択し、「セキュリティグループを作成」を押す
  3. 以下の内容で設定し、作成を押す
    [基本的な詳細]
    セキュリティグループ名 : session3-sg-for-rds
    説明 : 任意（例 : SG for RDS in session 3)
    VPC : session2-vpc(第2回で作成したもの)

    [インバウンドルール]
    タイプ : MySql/Aurora(スクロールダウン選択)
    ソース : session2-sg(第2回で作成したEC2にアタッチされたセキュリティーグループをスクロールダウン選択。)

DBエンジン MySQL

※ 以降の手順は以前の無料プランを利用しているアカウントでの作成手順になります。新しい無料プランを使用しているアカウントでは、表示や手順が異なる場合があります。

  1. 左メニューからAurora and RDSを選択する
  2. 「データベースの作成」を押す
  3. MySQLを選択する
  4. 無料枠を選択する(シングルAZが適用される)
  5. DBインスタンス識別子とパスワードを設定する
    DBインスタンス識別子 : database-session3(任意)
    マスターユーザー名 : admin(そのまま 任意で変更可)
    パスワード : 任意の値を設定(忘れないようにする)
  6. DBインスタンスクラスはそのまま
  7. ストレージはそのまま
  8. VPCはsession2-vpcを選択、DBサブネットグループはsession3-db-subnet-group(先ほど作成したもの)を選択する

  11. データベース作成中の画面が表示されるので、完了するまで数分待ちます。完了するとステータスが「利用可能」に変わりますが、待っている間にEC2のSSH接続を進めましょう。

  4. 以下の接続コマンドを入力する（RDSエンドポイントは控えておいたものを使用）
    パスワード入力を求められるので、RDS作成時に設定したパスワードを入力する。 
    5. mysql -h <RDSエンドポイント> -u admin -p

    接続が成功すると、MySQLのプロンプトが表示されます。

  5. ログイン後に以下のSQLを実行する
    6. create database testdb;
use testdb;
create table sample (id int, name varchar(50));
insert into sample values (1, 'test');
select * from sample;

    以下のように表示されれば、成功です

  6. データベース操作が完了したら、以下のコマンドで接続を終了します 
    7. exit;

後片付け

  1. EC2を削除する(削除方法は第2回参照)
  2. RDSを削除するため、アクションから「削除」を選択する
  3. 「最終スナップショットを作成する」「自動バックアップを保持」のチェックを外し、その下の自動バックアップが利用不可となることの了承にチェックをつける。 delete meを入力し、「削除」を押す
  4. DBインスタンスの削除中の画面が表示されるので、完了するまで数分待つ
