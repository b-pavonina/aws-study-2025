第6回：Dockerの基本とコンテナ化入門

Posted at 2025-12-30

1. はじめに

これまでは EC2（仮想サーバー）を中心に学んできましたが、近年は「コンテナを実行する基盤」として ECS（特にFargate） がよく使われます。

ただし ECS は「サーバーを立てるサービス」ではなく、コンテナを実行するサービスです。
そのため、ECSを使うにはまず Dockerイメージ（コンテナの元になる成果物） を自分で作れる必要があります。

そこで今回はAWSサービスではなく、ローカル環境でDockerを操作 して「イメージを作り、起動し、ログを見て、止めて消す」までを一通り体験します。
この流れを理解しておくと、次回のECS（Fargate）で詰まりやすいポイント（ポート、起動コマンド、ログ確認）が一気に見通せるようになります。

✅ なぜECSの前にDockerを学ぶのか（重要）

ECS（Fargate）は「コンテナをAWS上で実行・管理する仕組み」です。つまり、ECSが扱う“荷物”は Dockerイメージです。Dockerが分からないままECSに進むと、よくあるトラブルが 「原因不明」になりやすいです。

  • イメージを作れない：Dockerfileが書けないと、ECSに載せる“成果物”が作れません。
  • 起動失敗の理由が読めない：ECSで「タスクが落ちる」原因は、ほとんどが コンテナ内部の起動コマンド / ポート / 依存関係です（Dockerの知識が必要）。
  • 設定の対応関係が見えない：Dockerの docker run オプションは、ECSの タスク定義（portMappings / env / command 等）と対応します。

なので今回は「ECSを理解するための前提スキル」として、Dockerを先に固めます。

2. ゴール

  • コンテナの正体：コンテナは「軽量VM」ではなく「隔離されたプロセス」であることを理解する
  • Dockerの基本3点：Dockerfile（設計図）→ Image（成果物）→ Container（実行体）を説明できる
  • 基本操作：build / run / ps / logs / stop / rm / rmi を一通り実行できる
  • ポート公開：ホストとコンテナの通信（-p の意味）を理解する
  • ECSへの接続：今回の docker run と、次回のECSタスク定義の対応を言語化できる

3. 解説（Lecture）

3.1 仮想マシン（EC2） vs コンテナ

まず結論から言うと、コンテナは「OSを丸ごと持ちません」。 コンテナの正体は「OS上で動くプロセス」を、あたかも別マシンのように見せている仕組みです。

🔎 仕組みの要点（なぜ軽いのか）
  • VM（EC2など）：ハイパーバイザ上で「OS（カーネル含む）」を丸ごと起動します。OS起動が重く、 1台あたりのオーバーヘッドも大きいです。
  • コンテナ：OS（カーネル）は共有しつつ、プロセスを隔離します。つまり「OS起動」が不要で、 必要なのはアプリを動かすプロセス起動だけなので速いです。

では「隔離」はどう実現しているのでしょうか。代表的には次の3つがポイントです。

  • Namespaces（見える世界を分ける）
    プロセスID、ネットワーク、ユーザー、マウント（ファイルシステム）などを分離し、 コンテナの中からは「自分だけの世界」に見えるようにします。
  • cgroups（使える資源を制限する）
    CPU・メモリ・I/Oなどをグループ単位で制限し、「このコンテナが暴走してもホスト全体を巻き込まない」ようにします。
  • Union FS / レイヤー（差分で配布する）
    イメージはレイヤーの積み重ねです。変更分だけを追加して配布できるので、再利用が効きます（高速＆省容量）。
⚠️ Mac/Windowsの注意（「カーネル共有」の現実）

Linux上ではコンテナはホストのLinuxカーネルを共有します。一方、Mac/WindowsではそのままではLinuxカーネルが無いので、 Docker Desktop や OrbStack は内部で Linuxの軽量VM を動かし、その中のLinuxカーネルを共有してコンテナを動かします。

なので「コンテナ=OS共有」は原理として正しいのですが、Mac/Windowsでは「Linux VMの中で共有している」と理解すると混乱しません。

✅ まとめ：コンテナのメリットが“なぜ”生まれるか
  • 軽量：OS起動がなく、プロセス隔離なのでオーバーヘッドが小さい
  • 起動が速い：VM起動ではなく、プロセス起動だから速い
  • 同じ動き（Portability）：アプリ＋依存ライブラリ＋設定をイメージに閉じ込めるので、 実行環境のズレが起きにくい

3.2 Dockerの3要素（Dockerfile / Image / Container）

Dockerを学ぶときは「設計図 → 成果物 → 実行体」で考えると分かりやすいです。

  • Dockerfile：設計図（レシピ）。どんな環境を作り、何を入れ、どう起動するかを書きます。
  • Image：Dockerfileから作られた読み取り専用の成果物。配布・再現の単位になります。
  • Container：Imageを元に起動した「実行中のプロセス」。止めたり消したりできます。
🔎 初心者が詰まりやすいポイント（超重要）
  • イメージは基本“不変”：HTMLを書き換えても、すでに作ったイメージは変わりません（後で体験します）。
  • コンテナは“一時的”：コンテナを消すと中の変更も消えます（永続化は volume / DB を使う）。

3.3 ポートフォワーディング（-p オプション）

コンテナの中の世界とホストPCは隔離されています。そのため、コンテナ内部のWebサーバー（例：80番）へ ホストからアクセスするには「入口」を作る必要があります。それが -p です。

例：-p 8080:80 は「ホストの8080番 → コンテナの80番」へ転送します。

✅ 次回（ECS）との対応
  • Docker：docker run -p 8080:80 ...
  • ECS：タスク定義の portMappings（containerPort / hostPort）に相当

4. ハンズオン（Hands-on）

今回の方針

まずは「Dockerの仕組み」を学ぶことに集中するため、アプリは最小の静的HTMLにします。 nginx を使うので、言語の依存関係エラーに悩まされにくい構成です。

Step 0: Docker をインストール

Mac（推奨）
  1. Docker Desktop をインストールして起動します（初回は権限許可が求められることがあります）。
  2. ターミナルで以下を実行し、バージョンが出ればOKです。
docker version
docker run --rm hello-world

代替として OrbStack でもOKです（Mac向け）。導入が軽く、dockerコマンド互換で動きます。

Windows（推奨）
  1. Docker Desktop をインストールします。
  2. 案内に従って WSL2 を有効化します。
  3. PowerShell / ターミナルで以下を実行し、バージョンが出ればOKです。
docker version
docker run --rm hello-world
⚠️ うまくいかない場合
  • docker コマンドが見つからない：Docker Desktop の起動とPATHを確認します（再起動で直ることもあります）。
  • 権限エラー：会社PCでインストール権限が無い場合は、別手段（社内許可 or 代替PC or Linux環境）を検討します。

Step 1: ファイルの準備

作業用ディレクトリ docker-intro を作成し、その中にファイルを用意します。
VS Codeのエクスプローラーなどで作成します。

作成するファイル構成 
docker-intro/
  ├─ index.html
  └─ Dockerfile

index.html を作成します。

<!DOCTYPE html>
<html lang="ja">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Hello Docker</title>
  </head>
  <body>
    <h1>Hello Docker World</h1>
    <p>This page is served from inside a container.</p>
  </body>
</html>

Step 2: Dockerfile の作成

nginx:alpine をベースにします。軽量で、静的ファイル配信に向いています。 

FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
🔎 Dockerfile 命令の意味
  • FROM：ベースになるイメージ（材料）を指定します
  • COPY：ホストのファイルを、イメージ内にコピーします

Step 3: イメージのビルド（Build）

ターミナルで docker-intro ディレクトリに移動してから実行します。

cd docker-intro
docker build -t my-web-app .
🔎 オプションの意味
  • -t：イメージに名前（タグ）を付けます
  • 最後の .：Dockerfile を探す場所（カレントディレクトリ）です

ビルド後、イメージ一覧を確認します。

docker images

Step 4: コンテナの起動（Run）

docker run -d -p 8080:80 --name my-container my-web-app
🔎 オプションの意味（ECSにも効きます）
  • -d：バックグラウンド実行
  • -p 8080:80：ホスト8080番 → コンテナ80番へ転送
  • --name：コンテナに名前を付ける（ログや操作が楽になります）

稼働状況を確認します。

docker ps

Step 5: 動作確認

ブラウザで http://localhost:8080 にアクセスし、HTMLが表示されれば成功です。

追加で「中身」を覗く（コンテナ=プロセス隔離の体感）

コンテナ内でシェルを動かして、配置したファイルが見えるか確認します。

docker exec -it my-container sh
ls -la /usr/share/nginx/html
exit

ログを確認します。

docker logs my-container

Step 6: 変更と再ビルド（イメージの不変性を体験）

VS Codeで index.html の中身を書き換えて保存してください（例：Hello Docker World v2）。
ブラウザをリロードしても表示が変わらないことを確認します。

これは「すでに起動中のコンテナは、過去に作ったイメージを元に動いているため」です。
反映させるには「止める→消す→作り直す」が必要です。 

docker stop my-container
docker rm my-container
docker build -t my-web-app .
docker run -d -p 8080:80 --name my-container my-web-app

もう一度 http://localhost:8080 を開き、変更が反映されればOKです。

補足：なぜ今回は volume（-v）を使わないのか

volume（バインドマウント）を使うと「編集→即反映」ができて便利ですが、初心者の段階では “イメージは不変” という重要概念が曖昧になりがちです。 まずは再ビルドを体験して、ECSでのデプロイ感覚（新しいイメージを作って差し替える）に繋げます。

Step 7: 後片付け

docker stop my-container
docker rm my-container
docker rmi my-web-app
⚠️ よくある詰まりポイント
  • ポートが使用中（Address already in use）：8080が埋まっているので、 -p 8081:80 のように変えて試してください。
  • コンテナ名が重複：--name my-container が残っている場合は docker rm my-container で消します。
  • ログを見たい：docker logs my-container で確認できます。

5. 次の一歩（AWSへの接続）

今回ローカルで作った「イメージ」を、次回はAWSに持っていきます。流れは次の通りです。

  • ECR：作ったイメージを保存する場所（「Dockerイメージのレジストリ」）
  • ECS（Fargate）：そのイメージを使ってコンテナを実行・管理する
✅ 今日の学びが、次回ECSでどう効くか（3行で要点）
  • Dockerfile：ECSで動かすコンテナの「中身（実行環境）」を作る元になる
  • Image：ECRに置いて、ECSが取得して起動する“成果物”
  • docker run の考え方：ECSの「タスク定義（起動方法の設定）」に置き換わる

✅ Docker（ローカル）→ ECS（AWS）の対応表（次回のチートシート）
ローカルDocker 役割 ECS（次回）での対応
Dockerfile コンテナの中身を定義 同じ（イメージ作成の元）
docker build イメージを作る ビルドしてECRにpush
Image（タグ） 配布する成果物 ECRのリポジトリ（イメージURI）
docker run コンテナを起動 タスク定義 + サービス（またはRunTask）
-p 8080:80 ポートを外に公開 portMappings +（必要なら）ALB
docker logs ログを見る CloudWatch Logs
docker exec（任意） 中に入って確認 ECS Exec（設定すれば）

次回は「ローカルで docker run していた部分を、AWSでは タスク定義 に書き換える」と考えると理解しやすいです。

6. まとめ

  • コンテナは「OSを丸ごと起動するVM」ではなく「隔離されたプロセス」である
  • Dockerfile → Image → Container の流れを理解し、操作できるようになった
  • -p によるポート公開を体験し、ECSのportMappingsへの橋渡しができた
  • 「イメージは不変」を再ビルドで体感し、ECSのデプロイ感覚につながった
