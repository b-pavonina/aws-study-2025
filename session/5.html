第5回：S3静的サイトとCloudFront（CDN）の基本

Posted at 2025-12-30

1. はじめに

今回のテーマは、静的サイトを「速く・安全に・本番運用に近い形」で配信する基本を理解することです。
本セッションでは、以下のサービス群の役割と連携を学びます。

  • S3：HTML/CSS/JSなどの静的ファイルを保管するストレージ（配信元の格納場所）
  • CloudFront：世界中のエッジから配信するCDN（キャッシュによる高速化）
  • Route 53：独自ドメインをCloudFrontへ向けるDNS
  • ACM：HTTPS（TLS証明書）を発行・管理するサービス
  • OAC：S3を非公開にし、CloudFrontからのみ取得できるようにする仕組み
  • WAF / Shield：攻撃検知・遮断およびDDoS対策

進め方は、まず S3＋CloudFrontで配信を成立させるところまでをハンズオンで実施 します。
その後「次の一歩」として、独自ドメインやセキュリティ（OAC/WAF）の位置づけを整理します。

⚠️ 課金に関する注意

CloudFrontはデータ転送量やリクエスト数に応じて課金が発生します。また、WAFやRoute 53を利用する場合もコストがかかります。
ハンズオン終了後は必ずリソースを削除してください。

2. ゴール

ハンズオンで達成すること（完走ライン）

  • S3に index.html を配置し、CloudFront経由で表示できる
  • CloudFrontのキャッシュ（更新が即時反映されない理由）を体験できる
  • 更新反映の代表的な手段（Invalidation / TTL / Cache-Control）の存在を理解する

座学＋次の一歩で理解すること（理解ライン）

  • Route 53：独自ドメインをCloudFrontへ向ける考え方
  • ACM：CloudFront用証明書は us-east-1（バージニア北部） で発行が必要であること
  • OAC：S3を非公開にし、CloudFrontのみが取得できる構成（推奨形）
  • WAF/Shield：公開配信での防御レイヤの全体像

3. 解説（用語と役割）

3.1 S3：静的ファイルの置き場（オブジェクトストレージ）

S3は「ファイルを保管し、必要に応じて取り出す」ためのストレージです。
本セッションでは、S3を Webサーバーとしては使いません（= S3静的Webホスティング機能は利用しません）。
S3はあくまで オリジン（配信元） として扱い、配信の入口はCloudFrontに寄せます。

  • S3：配信元（Origin）
  • CloudFront：配信の入口（Distribution）

3.2 CloudFront：CDN（キャッシュ配信）

CloudFrontは、利用者に近いエッジから配信することで、高速化・負荷分散・安定配信を実現します。
キャッシュとは、CloudFrontが取得したコンテンツを一定期間保持し、次回以降の配信で再利用する仕組みです。
これにより高速化されますが、同時に 更新が即時反映されない ことがあります。

重要：Default root object

S3（REST API）をオリジンにした場合、ドメインルート（/）にアクセスしても自動で index.html は補完されません。
そのためCloudFront側の設定で Default root object = index.html を指定する必要があります。

3.3 Route 53：DNS

DNSは、aws.cloud-n-code.com のようなドメイン名を、CloudFront等の配信先に紐づける仕組みです。
CloudFrontへ向ける場合は、Aレコードの Alias（エイリアス） 機能を使用します。

3.4 ACM：HTTPS（TLS証明書）

ACMは、HTTPS化に必要な証明書を発行・管理するサービスです。

⚠️ リージョン注意

CloudFrontで使用するACM証明書は、必ず us-east-1（バージニア北部） リージョンで発行する必要があります。東京リージョンで発行してもCloudFrontでは選択できません。

3.5 OAC：S3を非公開にする（推奨）

S3を全面公開すると、意図しない公開事故のリスクがあります。
OAC（Origin Access Control） を使うことで、S3自体は非公開（Block Public Access ON）のまま、CloudFrontからのアクセスだけを許可する構成が作れます。これが実務での推奨構成です。

3.6 WAF & Shield：防御レイヤ

  • WAF (Web Application Firewall)：SQLインジェクションやXSSなどの攻撃、Bot、過剰アクセスを入口で遮断します。
  • Shield：DDoS攻撃対策です。Standard（標準）とAdvanced（有料・強化版）があります。

4. ハンズオン

今回は CloudFront（Distribution）＋ S3（Origin） で配信を成立させます。
S3静的Webホスティング機能は 無効 のまま進めます。

Step 1: S3バケット作成

  1. S3コンソールで「バケットを作成」をクリック
  2. バケット名：任意（例：aws-study-session5-static-yourname）
    ※世界で一意である必要があります。
  3. リージョン：アジアパシフィック（東京）
  4. ブロックパブリックアクセス：「パブリックアクセスをすべてブロック」に チェックを入れたまま（ON） にする
  5. 「バケットを作成」をクリック

Step 2: index.html をアップロード

  1. 作成したバケットを開き、以下の内容で作成した index.html をアップロードします。
<html>
<body>
  <h1>Hello CloudFront!</h1>
  <p>This is v1.</p>
</body>
</html>

アップロード後、ファイルをクリックして「オブジェクトURL」を開いてみてください。
Access Denied となり、表示できないはずです（S3が非公開のため）。

Step 3: 一時的にS3を公開して表示確認（暫定）

⚠️ 注意

この手順は学習のために一時的に実施します。実務ではOAC（後述）を使い、この手順は行いません。

  1. バケットの「アクセス許可」タブを開く
  2. ブロックパブリックアクセス：「編集」→ チェックをすべて外して保存（確認入力が必要）
  3. バケットポリシー：「編集」→ 以下のJSONを貼り付けて保存
    ※YOUR-BUCKET-NAME の部分を自分のバケット名に書き換えてください。 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "PublicReadGetObject",
            "Effect": "Allow",
            "Principal": "*",
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*"
        }
    ]
}

設定後、再度オブジェクトURLにアクセスし、ページが表示されることを確認します。

Step 4: CloudFront Distribution 作成

  1. CloudFrontコンソールで「ディストリビューションを作成」をクリック
  2. オリジンドメイン：プルダウンから先ほどのS3バケットを選択
  3. オリジンアクセス：今回は「Public」のまま（Step 3で公開済みのため）
  4. デフォルトルートオブジェクト (Default root object)：index.html と入力 （必須）
  5. 残りはデフォルトのまま「ディストリビューションを作成」をクリック

作成後、ステータスが「Deploying」になりますが、ドメイン名（xxxxx.cloudfront.net）はすぐに発行されます。
ブラウザでアクセスし、S3と同じページが表示されることを確認します。

Step 5: キャッシュ体験（更新が即時反映されない）

  1. PC上の index.html を編集（例：v1 → v2）し、S3に上書きアップロードします。
  2. CloudFrontのURLにアクセスします。更新が反映されず、古い内容（v1）が表示されることを確認します。
    ※これが「キャッシュ」です。
  3. Invalidation（キャッシュ削除）：
    • CloudFrontコンソールの「キャッシュ削除 (Invalidations)」タブ → 「キャッシュ削除を作成」
    • オブジェクトパス：/* （すべて削除）
    • 作成をクリック
  4. 完了後、ブラウザをリロードして更新（v2）が反映されることを確認します。

5. 次の一歩（本番運用に寄せる）

ハンズオンでは「まず動かす」ことを優先しましたが、本番運用では以下の構成を目指します。

5.1 OACでS3を非公開化（推奨形）

S3をインターネットに全公開するのはリスクがあります。
OAC を設定し、S3のバケットポリシーを「CloudFrontからのアクセスのみ許可」に書き換えることで、S3を非公開（Block Public Access ON）に戻せます。

5.2 Route 53 + ACMで独自ドメイン＆HTTPS

cloudfront.net ではなく独自のドメインで配信する場合です。
ACM（us-east-1）で証明書を発行し、CloudFrontにセット。Route 53のAliasレコードで紐付けます。

5.3 WAF & Shieldで防御

CloudFrontにWAF（Web ACL）を関連付けることで、SQLインジェクションや過剰なアクセス（DDoSの一種）を入口で防ぐことができます。

6. 後片付け（コスト事故を防ぐ）

  1. CloudFront：ディストリビューションを「無効化」し、その後「削除」します。
    ※削除完了まで時間がかかる場合があります。
  2. S3：
    • バケットの中身（index.html）を削除
    • バケットポリシーを削除
    • ブロックパブリックアクセスを「ON」に戻す
    • バケット自体を削除

7. まとめ

本セッションでは、S3に置いた静的ファイルをCloudFrontで配信する構成を通じて、以下を学びました。

  • S3：配信元（格納場所）。Webサーバー機能は使わず、単なるストレージとして利用。
  • CloudFront：配信の入口。キャッシュにより高速化するが、更新反映にはInvalidation等が必要。
  • Default root object：RESTオリジン構成では必須の設定。
  • 次の一歩：実務ではOACによる非公開化、Route 53/ACMによる独自ドメイン化、WAFによる防御を組み合わせる。
