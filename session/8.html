第8回：サーバーレスAPIの作成(Lambda + API Gateway)

※この回の勉強会では上記資料を使用しました。なお、「はじめに」以降の内容は上記資料をもとに作成したものではなく、管理人の備忘録として記載しています。作成途中の内容を含むため、正確性は保証できません。

1. はじめに

これまでの回では、Webサーバーやコンテナを使ってアプリケーションを動かす方法を学んできました。 ただ、実際の開発では「少しだけバックエンド処理がほしい」「フロントエンドからJSONを返すAPIがほしい」「でもサーバーの台数管理やOS更新まではやりたくない」という場面がよくあります。

そのときに強力な選択肢になるのが、Lambda + API Gateway によるサーバーレスAPIです。 サーバーを自分で起動・管理しなくても、HTTPリクエストを受けて処理し、JSONレスポンスを返すAPIを作れます。

今回は、API Gateway の HTTP API と AWS Lambda を組み合わせて、 ブラウザや curl から呼び出せるシンプルなAPIを作成します。 ただ動かすだけではなく、 「なぜ API Gateway が必要なのか」「Lambda はどこまで面倒を見てくれるのか」「ブラウザ連携でなぜ CORS が必要なのか」まで、実務につながる形で整理していきます。

⚠️ 課金に関する注意

Lambda と API Gateway は少量であれば安価に使いやすいサービスですが、無料利用枠の条件や利用量によっては料金が発生します。 また、CloudWatch Logs に出力したログにも料金がかかる場合があります。 学習後は不要な Lambda 関数、API Gateway、関連ログを削除するようにしてください。

この回の位置づけ

今回の内容は、静的サイトやフロントエンドからバックエンドAPIを呼び出すための入口になります。 今後、投稿機能や問い合わせ機能、外部連携APIなどを作るときの基礎になります。

2. ゴール

  • サーバーレスAPIの考え方と、Lambda / API Gateway の役割分担を説明できるようになる
  • HTTP API を使って GET / POST のエンドポイントを公開できるようになる
  • Lambda で JSON レスポンスを返す基本形を理解する
  • ブラウザ連携で必要になる CORS の意味を理解する
  • エラー時に API Gateway と CloudWatch Logs を使って原因を切り分けられるようになる

3. 解説

3-1. そもそもAPIとは何か

API は、アプリケーション同士がデータをやり取りするための窓口です。 たとえば、ブラウザ上のJavaScriptが「一覧データを取得したい」と思ったとき、 バックエンドに GET /items のようなリクエストを送り、JSONを受け取ります。

つまりAPIは、フロントエンドとバックエンドをつなぐ約束です。 URL、HTTPメソッド、リクエスト形式、レスポンス形式が決まっていると、画面側と処理側を分担して開発しやすくなります。

3-2. なぜサーバーレスなのか

通常のサーバー運用では、OSの管理、ミドルウェアの更新、スケーリング、障害対応などを考える必要があります。 学習用途や小さなAPI、イベント駆動の処理では、これらの運用負荷が大きく感じられることがあります。

AWS Lambda は、サーバーを管理せずにコードを実行できるコンピューティングサービスです。 AWS公式ドキュメントでも、サーバー管理不要、需要に応じた自動スケーリング、従量課金が特徴として説明されています。 また、Lambda は実行基盤側でキャパシティやOS管理、ログ出力などを担ってくれます。

つまりサーバーレスは、 「サーバーが存在しない」ではなく、「サーバー運用を利用者が意識しにくくなる」 という考え方です。

3-3. Lambda の役割

Lambda は、受け取ったイベントをもとに処理を実行する場所です。 今回は API Gateway から渡される HTTP リクエスト情報を受け取り、 条件に応じて JSON を返す関数を作ります。

Lambda では、Node.js や Python など複数のランタイムが利用できます。 2026年3月時点のAWS公式ドキュメントでは、Node.js 24 / 22 / 20 など複数の Node.js ランタイムがサポートされています。

初学者のハンズオンでは、書きやすさと動作確認のしやすさから Node.js か Python を選ぶことが多いです。 今回は JSON の扱いがわかりやすいように Node.js を使用します。

3-4. API Gateway の役割

API Gateway は、HTTP リクエストを受け付ける「表玄関」です。 AWS公式では、APIの作成・公開・保守・監視・保護を行うサービスであり、 バックエンドの EC2、Lambda、Webアプリなどへのフロントドアとして振る舞うと説明されています。

フロントエンドや外部クライアントは API Gateway にアクセスし、 API Gateway が背後の Lambda を呼び出します。 これにより、URL設計、認可、CORS、ログ、将来的なルーティング追加などを整理しやすくなります。

3-5. 今回 HTTP API を選ぶ理由

API Gateway には大きく REST API と HTTP API があります。 AWS公式ドキュメントでは、REST API はより多くの機能を持ち、HTTP API は最小限の機能で低価格に提供されると説明されています。

観点 HTTP API REST API
向いている用途 シンプルなAPI、学習用、小〜中規模のバックエンド 高度なAPI管理が必要な本番API
価格感 比較的安価 HTTP APIより高機能、そのぶん重め
特徴 CORS設定、JWT認可、Lambda統合を手軽に使いやすい APIキー、クライアントごとのレート制限、リクエスト検証、WAF統合、Private API などが使える

今回の教材では、まず「APIを公開して呼び出せる」ことに集中したいので HTTP API を選びます。 ただし、本番で APIキー管理・厳密なリクエスト検証・WAF・Private API が必要であれば、REST API を選ぶ判断も重要です。

3-6. リクエストはどう流れるのか

HTTP API の Lambda プロキシ統合では、クライアントが API を呼ぶと、API Gateway がリクエスト情報を Lambda に渡し、Lambda のレスポンスをそのままクライアントへ返します。

HTTP API のペイロード形式 2.0 では、たとえば HTTP メソッドは event.requestContext.http.method、 クエリ文字列は event.queryStringParameters、本文は event.body から取得できます。

また、レスポンスを細かく制御したい場合は、 statusCode、headers、body を含むオブジェクトを返します。 この形が崩れると期待どおりに返せず、エラーの原因になります。 

{
  statusCode: 200,
  headers: {
    "Content-Type": "application/json; charset=utf-8"
  },
  body: JSON.stringify({ message: "Hello" })
}

3-7. ブラウザ連携で CORS が必要になる理由

静的サイトを S3 や CloudFront で公開し、そこから別ドメインの API Gateway を呼ぶと、ブラウザはセキュリティ上の理由でクロスオリジン通信を制限します。 これが CORS の問題です。

AWS公式ドキュメントでも、HTTP API の CORS は別オリジンのWebアプリからAPIを呼ぶときに必要であり、設定すると API Gateway がプリフライトの OPTIONS へ自動応答し、設定済みのCORSヘッダーを付与すると説明されています。さらに、HTTP API 側で CORS を設定した場合、バックエンドが返した CORS ヘッダーは無視されます。

そのため、学習段階では「Lambda 側でも CORS ヘッダーを返す」ではなく、 まず API Gateway 側で CORS を設定すると考えると整理しやすいです。

3-8. この構成の良いところと限界

Lambda + API Gateway の構成は、少ない手間で API を公開できるのが強みです。 一方で、処理が大きくなってくると、関数分割、認証、エラーハンドリング、データベース接続、IaC 化などを考える必要があります。 今回はまず土台を作ることが目的なので、最小構成で理解を固めましょう。

4. ハンズオン

このハンズオンでは、1つの Lambda 関数に GET /hello と POST /hello をつなぎ、 API Gateway の HTTP API として公開します。 最後に curl とブラウザで動作確認し、必要であれば CORS も有効化します。

事前準備
  • AWS マネジメントコンソールにログインできること
  • 作業リージョンを決めていること（例: 東京リージョン）
  • curl または Postman など、HTTP リクエストを送れる環境があること
  • 所要時間の目安は 45〜60 分程度

4-1. 作るもの

今回作る API は次の2つです。

  • GET /hello?name=Yutaka → 名前付きのメッセージを返す
  • POST /hello → JSON本文を受け取り、その内容を返す

4-2. Lambda 関数を作成する

  1. AWS マネジメントコンソールで Lambda を開きます。
  2. 関数の作成 を押します。
  3. 一から作成 を選択します。
  4. 関数名に session8-hello-api など、わかりやすい名前を入力します。
  5. ランタイムは、コンソールで選択可能なサポート中の Node.js ランタイムを選びます。学習用としては新しめの LTS 系を選べば問題ありません。
  6. 実行ロールは 基本的な Lambda アクセス権限で新しいロールを作成 を選びます。
  7. 関数の作成 を押します。

関数が作成できたら、コンソール上のコードを次の内容に置き換えて Deploy してください。 

export const handler = async (event) => {
  console.log('event:', JSON.stringify(event, null, 2));

  const method = event?.requestContext?.http?.method || 'GET';

  if (method === 'GET') {
    const name = event?.queryStringParameters?.name || 'world';
    return response(200, {
      message: `こんにちは、${name} さん`,
      method: 'GET'
    });
  }

  if (method === 'POST') {
    let requestBody = {};

    try {
      requestBody = event?.body ? JSON.parse(event.body) : {};
    } catch (error) {
      return response(400, {
        message: 'JSON の形式が不正です'
      });
    }

    const name = requestBody.name || 'anonymous';
    const message = requestBody.message || 'メッセージなし';

    return response(200, {
      message: 'POST リクエストを受け取りました',
      received: {
        name,
        message
      },
      method: 'POST'
    });
  }

  return response(405, {
    message: '許可されていないメソッドです'
  });
};

const response = (statusCode, payload) => ({
  statusCode,
  headers: {
    'Content-Type': 'application/json; charset=utf-8'
  },
  body: JSON.stringify(payload)
});

このコードのポイントは次のとおりです。

  • HTTP メソッドを見て GET と POST を分岐している
  • GET ではクエリ文字列の name を読む
  • POST では JSON 本文を JSON.parse() で読む
  • レスポンスは statusCode と body を含む形で返す
  • console.log() で event を出力し、CloudWatch Logs で中身を確認できるようにしている

4-3. Lambda 単体でテストする

API Gateway をつなぐ前に、まず Lambda 単体で最低限の動作確認をしておくと安心です。 Lambda コンソールの テスト から、次のようなイベントを作成して実行してください。

GET 用のテストイベント例
{
  "requestContext": {
    "http": {
      "method": "GET"
    }
  },
  "queryStringParameters": {
    "name": "Yutaka"
  }
}
POST 用のテストイベント例
{
  "requestContext": {
    "http": {
      "method": "POST"
    }
  },
  "body": "{\"name\":\"Yutaka\",\"message\":\"serverless API の練習中です\"}"
}

4-4. API Gateway の HTTP API を作成する

  1. AWS コンソールで API Gateway を開きます。
  2. API を作成 を押します。
  3. HTTP API の 構築 を選びます。
  4. 統合先として Lambda を選び、先ほど作成した session8-hello-api を指定します。
  5. ルートを追加します。少なくとも次の2つを作成します。
GET  /hello
POST /hello
  1. ステージはデフォルトの $default のままで問題ありません。
  2. 自動デプロイを有効にしたまま作成すると、変更がすぐ反映されて学習しやすいです。
  3. 作成後、表示される Invoke URL を控えます。

たとえば Invoke URL が次のような形なら、今回のAPIのURLはその後ろに /hello を付けたものになります。 

https://abc123defg.execute-api.ap-northeast-1.amazonaws.com

つまり、実際の呼び出し先は次のようになります。

GET  https://abc123defg.execute-api.ap-northeast-1.amazonaws.com/hello
POST https://abc123defg.execute-api.ap-northeast-1.amazonaws.com/hello

4-5. API を呼び出して動作確認する

まずは GET から試します。

ブラウザで確認
https://abc123defg.execute-api.ap-northeast-1.amazonaws.com/hello?name=Yutaka
curl で確認
curl "https://abc123defg.execute-api.ap-northeast-1.amazonaws.com/hello?name=Yutaka"

次のような JSON が返れば成功です。

{
  "message": "こんにちは、Yutaka さん",
  "method": "GET"
}

次に POST を試します。

curl -X POST "https://abc123defg.execute-api.ap-northeast-1.amazonaws.com/hello" \
  -H "Content-Type: application/json" \
  -d '{"name":"Yutaka","message":"serverless API の練習中です"}'

次のようなレスポンスが返れば成功です。

{
  "message": "POST リクエストを受け取りました",
  "received": {
    "name": "Yutaka",
    "message": "serverless API の練習中です"
  },
  "method": "POST"
}

4-6. ブラウザから呼ぶために CORS を有効化する

今の状態でも curl では動きますが、S3 や CloudFront で公開した静的サイトから fetch() で呼ぶと、CORS エラーになることがあります。 その場合は API Gateway の HTTP API 側で CORS を設定します。

  1. API Gateway で対象の HTTP API を開きます。
  2. CORS を選択します。
  3. 学習用なら一時的に Access-Control-Allow-Origin: * にしてもかまいません。
  4. 本番を意識するなら、静的サイトのドメインだけを明示します。例: https://aws.cloud-n-code.com
  5. 許可メソッドは GET, POST, OPTIONS を追加します。
  6. 許可ヘッダーは少なくとも content-type を追加します。
  7. 保存して再テストします。

フロントエンドからの確認用として、次のような fetch() も試せます。 

fetch('https://abc123defg.execute-api.ap-northeast-1.amazonaws.com/hello?name=Yutaka')
  .then((res) => res.json())
  .then((data) => console.log(data))
  .catch((err) => console.error(err));

4-7. CloudWatch Logs で中身を確認する

API がうまく動かないときは、まず Lambda 側のログを確認します。 今回のコードでは console.log('event:', ...) を入れているので、API Gateway からどのようなイベントが渡ってきたかを見られます。

  1. Lambda 関数を開きます。
  2. モニタリング タブを開きます。
  3. CloudWatch Logs を表示 を押します。
  4. 直近のログストリームを開き、event の内容とエラーメッセージを確認します。

4-8. よくあるハマりどころ

症状 主な原因 確認ポイント
502 Bad Gateway Lambda のレスポンス形式が不正 statusCode / body の返し方、JSON文字列化の有無を確認する
ブラウザだけ失敗する CORS 未設定 API Gateway の CORS 設定、許可オリジン、許可メソッドを確認する
POST で 400 になる リクエスト本文がJSONとして壊れている curl の -H "Content-Type: application/json" と本文の引用符を確認する
想定外のメソッドになる ルート設定の不足、URLの誤り API Gateway の Route と Invoke URL の組み合わせを確認する

4-9. 発展課題

  • /health を追加し、ヘルスチェック用レスポンスを返す
  • POST /hello で message が空なら 400 を返す
  • Lambda を1つではなく、ルートごとに関数分割してみる
  • API Gateway の認証やカスタムドメインを調べてみる
  • このAPIを、自分の静的サイトの fetch() から呼び出してみる

4-10. 後片付け

  1. 不要になった API Gateway の HTTP API を削除する
  2. 不要になった Lambda 関数を削除する
  3. 必要に応じて CloudWatch Logs のロググループも削除する

5. まとめ

今回は、Lambda と API Gateway を使って、サーバーレスAPIの最小構成を体験しました。 重要なのは、単に「動いた」で終わるのではなく、 API Gateway がHTTPの入口、Lambda が処理本体 という役割分担を理解することです。

また、HTTP API を使うとシンプルなAPIを比較的軽く作れますが、 すべての要件に万能というわけではありません。 APIキー、厳密な検証、WAF、Private API などが必要なら REST API の検討も必要です。 この切り分けができるようになると、設計の質が一段上がります。

次のステップとしては、今回作ったAPIを静的サイトの画面から呼び出し、 ユーザー入力を受けて一覧や登録処理を行う形に発展させると、より実務に近い理解につながります。
